# 명세에서 구현과 검증으로 이어지는 출장비 예제

고객 요구를 코드와 시험에 연결하는 첫 SDD 예제입니다. 숙박 일수를 입력하는 일반 웹 기능을 만들고, OCI 설명은 선택 기능으로 붙였습니다. 명세는 특정 개발 도구나 챗봇 없이 읽고 수정할 수 있는 파일입니다.

실제 고객 인터뷰 결과가 아니라 기존 학습 예제를 기준으로 정리한 합성 요구입니다. 기존 앱에 명세를 연결하고 오프라인 계산 확장을 설계부터 적용했습니다. 자동으로 모든 코드를 생성하는 시스템이라는 뜻은 아닙니다.

## 파일별 역할

| 파일 | 읽고 결정할 내용 |
|---|---|
| [spec.md](spec.md) | 사용자 목적, 요구 ID, 성공 조건, 제외 범위 |
| [design.md](design.md) | 코드 구조, API, OCI 선택 여부, 변경 경계 |
| [tasks.md](tasks.md) | 구현·검증 작업과 실제 완료 범위 |
| [traceability.json](traceability.json) | 요구별 구현 파일과 자동 테스트 위치 |
| [앱 소스와 실행 안내](../../examples/enterprise-ai-web/README.md) | 실제 실행과 코드 수정 |

## 계정 없이 확인하기

저장소를 복제하고 최상위에서 다음 명령을 실행합니다. Python 3.12 이상이면 되며 외부 패키지 설치·OCI 인증·Foundation 접근 권한이 필요하지 않습니다.

```sh
python3 scripts/check_spec_links.py specs/travel-allowance
python3 -m unittest discover -s examples/enterprise-ai-web -p 'test_*.py'
python3 examples/enterprise-ai-web/server.py --offline
```

첫 명령은 요구 ID와 코드·테스트 링크 존재를 검사하고 파일 해시를 출력합니다. `links_valid`는 테스트 합격이나 업무 요구 충족을 뜻하지 않습니다. 두 번째 명령이 실제 테스트를 실행합니다. 세 번째 명령 후 `http://127.0.0.1:8768`에서 숙박 2박을 선택하면 규정 한도 20만 원을 확인할 수 있습니다. 실제 AI 연결은 앱 안내의 선택 절차를 따릅니다.

## 요구를 바꾸는 순서

예를 들어 숙박 상한을 10박에서 14박으로 늘리려면 다음처럼 진행합니다. 이 변경은 설명용이며 현재는 10박입니다.

1. `spec.md`의 REQ-001에서 허용 범위와 성공·실패 예시를 수정합니다.
2. `design.md`에서 API·화면·검증 영향과 적용할 규정을 검토합니다.
3. `tasks.md`에 변경 작업을 추가합니다. `traceability.json`에서 관련 파일·테스트를 찾습니다.
4. `estimate` 입력 범위와 화면 선택지, 정상 14박·실패 15박 테스트를 함께 수정합니다.
5. 링크 검사와 실제 테스트를 다시 실행하고 변경 명세·코드·검증 결과를 함께 리뷰합니다.

요구를 만족하는지와 테스트가 충분한지는 사람이 확인합니다. 개발 도구에는 이 네 파일과 관련 코드를 입력으로 줄 수 있으며 특정 제품의 import·자동 동기화를 구현했다고 주장하지 않습니다.

## 확인한 범위

2026년 11월 9일 앱 테스트 12건과 링크 검사기 테스트 4건 통과. `python3 -S`로 외부 site-packages를 로드하지 않은 서버에서 2박 계산 HTTP 응답 `200000`, `model_used=false`, OCI 호출 경로 409 거부를 확인했습니다. 브라우저 시각 검증과 이 앱의 OCI 호스팅은 수행하지 않았습니다.

인터뷰 원문을 요구 초안과 검토 기록으로 옮기는 절차는 [인터뷰 근거 연결 도구](../interview-handoff/README.md)에서 확인할 수 있습니다. 현재 명세에 자동 병합하거나 코드·배포를 변경하지 않으며, 검토한 요구와 ID를 사람이 대조해 반영합니다. 같은 요구 ID에 실제 OCI 배포·인수 결과를 연결하는 것은 후속 단계입니다.
