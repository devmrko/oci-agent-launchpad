# OCI 고객 에이전트 공동 개발 프로그램 계획

작성일: 2026-11-05 | 상태: 검토용 초안 | 범위: 기획과 설계

## 목적과 기대 효과

고객의 실제 업무 문제를 해결하는 AI 에이전트를 함께 만들고, OCI에서 배포·검증한 뒤 고객의 상용 운영으로 연결하는 현장 프로그램을 제안합니다. CE, 고객 제품 책임자, 개발팀과 운영팀이 같은 성공 기준을 공유하고, 워크숍 이후의 책임과 후속 작업까지 정하는 것이 목적입니다.

첫 단계는 내부 리허설 1회와 고객 파일럿 2건입니다. 3일 워크숍의 완료 기준은 **합의한 업무 흐름이 OCI에서 동작하고 검증 결과와 운영 전환 계획이 남는 것**입니다. 상용 운영 준비가 완료됐다는 보장은 하지 않습니다. 후속 기간에는 품질·보안·운영 기준을 충족한 범위부터 제한적으로 운영합니다.

기대 효과는 고객이 가치를 확인하는 시간 단축, 현장별 반복 작업 감소, 운영 전환 책임 명확화입니다. 클라우드 사용량과 데이터베이스 도입은 함께 측정하되, 실제 업무 사용과 구분합니다.

## 녹취에서 도출한 문제와 대응

아래는 사용자가 제공한 녹취를 바탕으로 정리한 제안입니다. 개별 발언을 Oracle 전체 조직의 확정된 현황으로 일반화하지 않습니다. 인사 관련 발언, 연락처와 고객 실명은 기획에 필요하지 않아 포함하지 않았습니다.

| 녹취에서 제기한 문제 | 이번 계획의 대응 | 확인할 증거 |
| --- | --- | --- |
| 제품 설명 위주로 대화하면 고객이 만들려는 업무를 놓칠 수 있음 | 제품 책임자와 AI 개발자를 포함한 업무 발굴 인터뷰 | 고객이 합의한 문제, 현재 처리 방식, 성공 지표 |
| 로컬 시연 이후 클라우드 배포가 지연됨 | 워크숍 전에 계정·권한·리전·네트워크 준비 완료 | 준비 점검 기록과 최소 배포 시험 |
| 에이전트 실행·메모리·권한·관측을 일일이 구성해야 함 | 공통 운영 구성과 고객별 업무 코드를 구분 | [AgentCore 대체 구성 계획](oci-agent-platform-plan.md) |
| 인프라와 데이터 조직의 역할이 나뉘어 진행이 어려움 | 단일 딜리버리 책임자와 공동 기술팀 지정 | 역할표, 의사결정자와 후속 담당자 |
| POC와 후속 매출·운영 상태를 연결하기 어려움 | 고객 과제마다 동일한 식별자로 상태와 사용량 추적 | 기회 식별자, 배포일, 운영일, 비용·사용량 |
| 중앙 콘텐츠 재사용이 고객별 문제 해결과 충돌함 | 질문·운영·검증 절차를 재사용하고 업무 요구는 고객별로 설계 | 재사용률과 고객 수용 결과를 별도 측정 |

발표자가 언급한 매출, 개발 속도 배수, 워크숍 비용과 타사 채용 규모는 산정 근거를 확인하지 못한 경험·전언입니다. 이 계획의 사업성 근거 또는 고객 약속으로 사용하지 않습니다. 녹취의 상대 날짜도 현재 일정으로 환산하지 않습니다.

## AI-DLC에서 가져올 원칙

AI-DLC는 AI가 의도를 구체화하고 작업·설계를 제안하며, 사람이 중요한 판단과 결과 검증을 맡는 개발 방식입니다. 원문은 Inception, Construction, Operations를 설명하고, 의도(Intent), 가치 있는 작업 단위(Unit), 짧은 반복(Bolt)을 연결합니다. 기존 코드가 있는 경우에는 구조와 동작을 먼저 파악합니다. [AWS 방법론 원문](https://prod.d13rzhkk8cj2z0.amplifyapp.com/aidlc.pdf)

우리 프로그램에서는 AI가 질문과 초안을 만들고 고객이 업무 의미를 확인하게 합니다. 요구사항에서 테스트와 운영 결과까지 연결되는 기록을 남깁니다. AI가 작성했다는 이유만으로 설계나 코드의 정확성을 인정하지 않습니다.

개발을 지원하는 AI와 고객에게 제공할 업무 에이전트는 구분합니다. 전자는 개발 과정의 도구이고, 후자는 인증·데이터 접근·평가·운영이 필요한 애플리케이션입니다. AI-DLC 자체가 에이전트 호스팅 플랫폼을 제공하는 것은 아닙니다.

현재 공개 저장소는 여러 코딩 도구를 지원하는 공통 코어와 도구별 연동 구조를 설명하며, README의 단계 구성도 원문 방법론보다 확장되어 있습니다. 따라서 녹취의 파일명과 절차를 최신 저장소의 고정 규칙이라고 가정하지 않습니다. 구현 착수 시 사용할 릴리스 또는 커밋을 고정하고, 라이선스와 변경 범위를 확인합니다. [AI-DLC 공개 저장소](https://github.com/awslabs/aidlc-workflows)

3일 일정과 이후의 45일 운영 전환 목표는 이번 프로그램의 제안입니다. AI-DLC의 필수 기간으로 취급하지 않습니다.

## 고객과 첫 업무 선정

첫 파일럿은 내부 사용자가 고객·제품·업무 정보를 조회하고, 근거를 확인한 뒤 요청 초안을 만드는 업무를 권장합니다. 검색, 구조화된 데이터 조회, 도구 호출, 권한 통제와 관측을 한 흐름에서 검증할 수 있습니다. 결제, 실제 주문 확정, 외부 메시지 자동 발송은 첫 범위에서 제외합니다.

업무 발굴 인터뷰에서는 다음을 확인합니다.

1. 사용자가 누구이며 지금 어떤 일을 어떤 순서로 처리합니까?
2. 시간이 많이 들거나 오류가 발생하는 단계는 어디입니까?
3. 성공 여부를 어떤 결과와 수치로 판단합니까?
4. 어떤 데이터와 시스템이 필요하며 누가 접근을 승인합니까?
5. 에이전트가 제안만 할 일과 실제 실행할 일은 무엇입니까?
6. 실패했을 때 누가 처리하고, 상용 운영은 누가 맡습니까?

파일럿 후보는 업무 가치, 데이터 준비도, 외부 연동 복잡도, 평가 가능성, 고객 담당자의 참여 가능성으로 비교합니다. 점수 합계가 높아도 데이터 사용 권한이나 운영 책임자가 없으면 착수하지 않습니다. 기존 OCI 고객을 우선 검토하되, 특정 데이터베이스 사용 여부를 고객 수요의 대리 지표로 삼지 않습니다.

## 고객과 사전 합의할 조건

고객은 제품 책임자, 개발 리더, 데이터 담당자, 보안·운영 담당자를 지정합니다. CE 측은 딜리버리 책임자 1명과 플랫폼·데이터 담당 역할을 지정합니다. 실제 인원은 업무 복잡도에 맞추며, 참여자 수에 맞춰 인위적으로 기능을 쪼개지 않습니다.

워크숍 전 일주일 동안 다음을 완료합니다.

| 준비 항목 | 주 담당 | 완료 기준 |
| --- | --- | --- |
| 업무 설명과 범위 | 고객 제품 책임자 | 대표 사용자 여정, 포함·제외 기능, 수용 기준 합의 |
| 데이터와 연동 | 고객 데이터·개발 담당 | 사용 가능한 샘플, API 계약, 접근 권한과 비식별화 확인 |
| OCI 환경 | 고객 운영팀과 플랫폼 CE | 리전, 컴파트먼트, 모델 접근, 네트워크와 할당량 확인 |
| 비용과 종료 | 고객 예산 책임자 | 지출 한도, 비용 알림, 종료일, 삭제·보존 책임 합의 |
| 운영 기반 | 플랫폼 담당 | 최소 컨테이너 배포, 인증, 추적, 데이터 연결 사전 검증 |
| 평가 기준 | 고객 업무 전문가와 검증 담당 | 정상·오류·권한 거부 사례와 기대 결과 준비 |
| 후속 지원 | 딜리버리 책임자 | 운영 전환 담당자, 가용 시간, 첫 후속 회의 확정 |

배포 준비가 끝나지 않으면 일정을 조정하거나 설계 워크숍으로 범위를 변경합니다. 로컬 시연만으로 OCI 배포 완료를 보고하지 않습니다. 클라우드 사용 비용은 고객과 사전 합의하며, 미사용 자원을 유지해 소비량을 늘리지 않습니다.

## 3일 워크숍 운영안

| 시점 | 활동 | 산출물과 통과 조건 |
| --- | --- | --- |
| 1일차 오전 | 고객 의도 검토, AI의 질문에 공동 답변, 수용 기준 확정 | 요구사항과 미결정 사항, 고객 책임자 확인 |
| 1일차 오후 | 업무·데이터·권한 설계, 작업 분할, 첫 흐름 개발 | 설계 결정, 인터페이스 계약, 최소 기능 검증 |
| 2일차 오전 | 업무 기능 구현과 단위·통합 검증 | 대표 업무 흐름과 재현 가능한 테스트 |
| 2일차 오후 | OCI 개발 환경에서 조기 통합, 오류·권한·추적 검증 | 배포 후보, 실패 사례와 수정 목록 |
| 3일차 오전 | 배포 구성 확정, 수용·복구·비용 점검 | 검증된 OCI 엔드포인트, 운영 초안 |
| 3일차 오후 | 업무 성과 중심 시연과 인수 협의 | 수용 결과, 미충족 항목, 후속 일정과 책임자 |

배포 위험을 일찍 발견하기 위해 공통 기반은 사전에 준비하고, 2일차부터 OCI에서 통합합니다. 3일차에 처음 권한이나 네트워크 문제를 확인하는 일정은 피합니다.

AI가 요구사항, 설계, 작업 목록을 제안하되 중요한 업무 규칙·권한·비용·데이터 이동은 사람이 확정합니다. 요구 변경 시 연결된 설계와 평가 사례도 갱신합니다. 독립성이 있는 작업만 병행하며, 통합 담당자와 공통 인터페이스를 먼저 정합니다.

제품 설명은 고객의 실제 설계 선택과 연결합니다. 예를 들어 데이터 저장소의 장점은 필요한 트랜잭션·검색·운영 조건을 근거로 설명합니다. 제품 제약과 데이터 이동은 설계 초기에 드러내고, 3일차에는 최종 배포 선택과 비용을 확인합니다.

## 데이터베이스 선택 원칙

Oracle Database를 경험하는 트랙과 고객의 기존 데이터 계층을 유지하는 트랙을 구분해 제안합니다. 전자의 경우에도 목적, 기간과 비용을 사전에 알리고 고객 동의를 받습니다.

Oracle Database는 고객의 기존 데이터, 권한 모델, 운영 역량과 실제 필요한 기능을 바탕으로 검토합니다. 벡터·그래프·트랜잭션을 시연에 모두 넣는 것을 목표로 삼지 않습니다. PostgreSQL 등 다른 저장소가 적합하면 선택 이유를 기록하고 OCI 전체의 운영 가치와 별도로 평가합니다.

데이터베이스 교체는 접속 문자열 변경으로 끝난다고 약속하지 않습니다. 스키마, 쿼리, 검색 의미, 권한, 마이그레이션과 성능 검증이 필요합니다. 추상화할 인터페이스를 정하되 첫 파일럿에서 여러 데이터베이스를 동시에 구현하지 않습니다.

## 워크숍 이후 운영 전환안

워크숍 종료일부터 최대 45일을 초기 목표로 두되, 고객의 심사·연동 일정에 따라 조정합니다. 운영 전환 담당자는 워크숍 전에 지정하고, 종료 시 산출물을 직접 인수합니다.

| 기간 | 목표 | 다음 단계 조건 |
| --- | --- | --- |
| 종료 후 1주 | 미충족 요구 분류, 담당·일정·서비스 목표 확정 | 고객이 우선순위와 잔여 위험 수용 여부 결정 |
| 2~3주 | 권한, 데이터 처리, 회귀 평가와 부하·장애 검증 | 합의한 평가 기준과 중대 결함 해결 |
| 4~5주 | 제한 사용자 운영, 알림·지원·복구 훈련 | 실제 사용자 결과와 운영 담당자 인수 확인 |
| 6주 전후 | 운영 확대 또는 추가 보완 결정 | 고객의 명시적 운영 승인과 후속 책임 확인 |

상용 운영 승인은 업무 정확성, 권한 격리, 비용 상한, 감사 기록, 복구 절차, 지원 체계를 함께 검토합니다. 프롬프트에 주의를 주는 것만으로 보안 통제가 구현됐다고 판단하지 않습니다.

| 실행 환경과 공통 운영 기반 | 플랫폼 책임자 | 고객 운영·보안팀 |
| 데이터 의미와 접근 범위 | 고객 데이터 책임자 | 데이터 CE, 개발팀 |
| 구현 검토와 통합 | 고객 개발 리더 | CE, 필요 시 파트너 |
| 상용 운영 승인 | 고객 운영 승인권자 | 보안, 제품, 개발 책임자 |
| 후속 안정화 | 지정된 운영 전환 리더 | 고객 운영팀, COE·파트너 등 |

COE는 공통 기반, 검증 도구와 기술 지원을 제공하고 CE는 고객 문제 구체화와 현장 진행을 맡는 분담을 제안합니다. 특정 조직이 이를 수락했다고 가정하지 않습니다. 조직 간 성과 귀속은 파일럿 시작 전에 합의하고 고객 과제 하나를 중복 집계하지 않습니다.

## 프로그램 준비 일정과 확대 기준

아래는 승인 이후 시작할 상대 일정입니다. 지금은 실행하지 않습니다.

| 단계 | 예상 기간 | 산출물 |
| --- | --- | --- |
| 범위 합의 | 1주 | 파일럿 후보, 책임자, 예산 범위, 플랫폼 최소 요구 |
| 공통 구성 검증 | 1~2주 | 실행 환경 선택 근거, 권한·메모리·관측 시험 결과 |
| 내부 리허설 | 3일과 회고 | 진행자 가이드와 실패·복구 기록 |
| 고객 파일럿 2건 | 고객별 사전 1주와 워크숍 3일 | 업무 수용 결과와 OCI 배포 결과 |
| 운영 전환 관찰 | 고객별 최대 45일 목표 | 실제 사용, 품질·비용, 지원 부담 |
| 확대 판단 | 결과 검토 후 | 유지·보완·중단 결정과 다음 인력 계획 |

확대의 잠정 기준은 두 파일럿 모두 배포·추적·인수 기록을 갖추고, 최소 한 건이 고객 승인 아래 실제 업무에 사용되는 것입니다. 해결되지 않은 중대 권한 결함이 없고, 다음 담당자가 가이드만으로 재현할 수 있는지도 확인합니다. 이 기준은 초기 제안이며 파일럿 전에 책임자와 확정합니다.

## 성과 측정

첫 버전은 간단한 등록부로 시작합니다. 별도의 포털 개발은 반복 운영의 필요가 확인된 뒤 검토합니다.

| 측정 대상 | 정의 |
| --- | --- |
| 고객 가치 | 동일 업무의 처리 시간·완료율·오류율을 사전 기준선과 비교 |
| 최초 배포 시간 | 합의한 착수 시점부터 고객 OCI 환경의 검증된 첫 실행까지 |
| 운영 전환율 | 정해진 관찰 기간을 채운 파일럿 중 고객 운영 승인 건수 비율 |
| 사용 지속성 | 배포 후 실제 활성 사용자와 성공 업무 실행 추이 |
| 품질 | 고객 평가 세트 성공률, 권한 위반, 잘못된 도구 호출, 지연시간 |
| 비용 | 모델·컴퓨트·DB·저장·관측·네트워크 비용과 성공 업무당 비용 |
| 지원 효율 | 공통 구성 재사용, 고객별 수정 시간, 운영 전환 지원 시간 |
| 사업 결과 | 실제 청구·사용량, 확정 계약과 추정 파이프라인을 구분 |

등록부에는 과제 식별자, 고객 책임자, 기회 식별자, 업무 유형, 시작·배포·운영일, 상태, 실패 이유, 후속 담당자와 측정 기간을 둡니다. 크레딧 사용과 유료 청구를 구분하고, 한 달의 소비량을 12배 한 값을 확정 ARR로 보고하지 않습니다. 기술적으로 사용이 발생한 시점과 청구 자료에서 확인되는 시점도 구분합니다.

## 다음 검토에서 정할 사항

우선 기본안은 내부 조회·요청 초안 업무, 단일 고객 환경, 한 가지 데이터 저장소, 인증된 사용자와 제한된 도구입니다. [대체 구성 계획](oci-agent-platform-plan.md)을 검토한 뒤 다음을 확정합니다.

1. 첫 고객 업무와 수용 기준, 데이터 사용 가능 여부.
2. 대상 OCI 리전과 고객 테넌시에서 실제 사용할 수 있는 실행 환경.
3. 플랫폼·데이터·후속 운영을 맡을 책임자와 투입 시간.
4. Oracle Database 체험 트랙 또는 고객 기존 저장소 유지 트랙.
5. 파일럿 비용 한도, 기간과 확대 판단 기준.
