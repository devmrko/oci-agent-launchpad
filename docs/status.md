# 현재 상태 — 독립 플랫폼 파일럿과 Companion 연동

## 2026-11-09 전체 점검

최신 완료 범위와 다음 작업은 [기능·재현 배포 점검](design/platform-readiness-review.md)을 기준으로 본다. OKE 0.6.0 모델·메모리·Langfuse·PVC 보존이 검증됐고 Companion에는 독립 앱 등록, OCI 의존 리소스, Deployment/Pod/노드 조회가 반영됐다. 아래 11월 7일 이전 문단은 해당 시점의 기록이다. 과거 약 30% 수치를 현재 완료율로 사용하지 않는다. 전체 AgentCore 동등성과 새 고객 환경의 무개입 배포는 미완료다.

재현 설정의 첫 보완으로 [다중 앱 연결 생성기](../deploy/COMPANION-CONNECTIONS.md)를 추가했다. 기존 단일 agent-monitor 생성기는 호환용으로 남기며 현재 Companion 신규 연결에는 새 형식을 사용한다.

## 2026-11-07 관리형 빌드와 상시 관측 연결

현재 VM 서비스는 **0.5.0 · UP**이다. OCI 관리형 Linux 빌드·테스트 → Artifact Registry 전달 → 다운로드 무결성 검사 → OCI DevOps VM 배포가 모두 성공했다. 아래 11월 6일의 러너 확보 실패는 과거 기록이며 현재 빌드 차단 사유가 아니다.

- 앱과 Langfuse VCN 사이 사설 연결을 구성했고, 앱 사용자 권한으로 사설 LB까지 관측 이벤트 전달을 확인했다. 이 검증은 별도 시험 프로세스에서 수행했으며 배포된 서비스의 상시 전송 완료를 뜻하지 않는다.
- 배포된 0.5.0의 실제 OCI 모델 호출, Oracle Agent Memory 세션 간 저장·조회, 사설 LB를 통한 Langfuse 관측 5건 수신을 확인했다. 일반 합성 대화 입력·출력은 켰으며 메모리 본문은 제외된다.
- Artifact Registry 전달 단계의 DevOps 조회 권한 오류를 수정했다. 정확한 빌드 파이프라인 주체에 구획 내 읽기를 허용하며 테넌시 전체 관리 권한은 부여하지 않았다. 후속 Terraform plan은 No changes다.
- Companion 화면은 다른 확장 UI의 차단으로 이번 실행을 검증하지 못했다. 빌드는 OCI SDK로 시작했으며 Companion을 통한 전체 자동 완주로 표시하지 않는다.

자세한 빌드 결과는 [빌드 안내](../deploy/BUILD.md), 관측 검증과 한계는 [Langfuse 연결](../deploy/SERVICE-DESK-LANGFUSE.md)을 확인한다. 후속 작업으로 Companion의 성공 빌드 상세 → 배포 선택 → 파일 SHA-256·크기 검증 → 재배포 실행을 구현했고 실제 화면과 OCI API에서 SUCCEEDED, VM UP · 0.5.0을 확인했다. Companion은 Launchpad 전용 파일 형식을 읽지 않는다. 남은 부분은 새 버전의 파이프라인·VM manifest 등록과 산출물 승격 자동화다. 최초 빌드는 SDK로 시작했으며 새 버전 생성부터 무개입 전체 자동화가 된 것은 아니다.

2026-11-06. 전체 목표는 AI-DLC 템플릿으로 고객 요구를 구체화하고, 독립 AgentCore 대응 플랫폼 위에서 에이전트를 실행하며, OCI Companion으로 구축·빌드·배포·모니터링을 돕는 것입니다. 플랫폼을 만드는 과정에서 Companion에 없는 기능도 구현합니다.

**목표 조정: 먼저 동작하는 뼈대를 완성하고 그 위에서 기능을 발전시킵니다.** 사용자가 2026-11-06 확정했습니다. 아래 약 30%는 주요 기능까지 포함한 전체 목표의 이전 추정이며, 새 1차 목표의 완료율로 사용하지 않습니다.

## 1차 목표: 확장 가능한 동작하는 뼈대

1. **독립 실행:** 플랫폼은 Companion 없이 설정 파일과 CLI/API로 실행·호출할 수 있습니다. 예제 업무 코드와 공통 플랫폼 책임을 구분합니다.
2. **대표 기능:** 예제 하나에서 Runtime → 모델/도구 → Oracle Agent Memory → 실행 추적을 실제로 연결합니다. 기존 인증·승인·사용자 경계 검증을 유지합니다.
3. **빌드와 배포:** 고정 소스·Foundation 버전으로 패키지를 만들고, Companion에서 빌드를 요청하여 새 버전을 배포합니다. 빌드 ID·산출물 해시·배포 ID·실행 버전을 연결합니다.
4. **상태 확인:** Companion에서 health·버전·대표 실행 추적을 확인합니다. Companion 중지 시에도 실행 서비스가 동작하는지 별도로 검증합니다.
5. **확장 계약:** Memory·Gateway·Identity·Policy·관측·평가·Code Interpreter·Browser의 책임과 연결 지점을 정합니다. 실제 제공하는 기능과 미구현 기능을 명시하고, 미구현 호출은 성공처럼 처리하지 않습니다.
6. **재현:** 다른 환경 값을 넣어 준비·실행·검증할 수 있는 필수/옵션 설정과 절차를 제공합니다. 관리자 선행 작업과 자동화된 부분을 구분합니다.

**뼈대 완료 조건:** 위 항목의 실행 증거가 있고, 개발 PC에서 패키지를 수동 생성하거나 앱을 SSH 설치하지 않아도 Companion을 통한 새 버전 빌드·배포·상태 확인이 한 번 완주해야 합니다. 설정과 API를 재사용해 Companion 없이도 실행할 수 있어야 합니다. 빈 폴더·빈 인터페이스만 만든 상태는 완료가 아닙니다.

공통 OAuth 위임, 중앙 정책 엔진, 폭넓은 커넥터, 품질 평가 자동화, 격리 코드/브라우저 실행, 자동 확장·고가용성은 뼈대 이후 단계적으로 발전시킵니다. 이것들은 삭제된 요구가 아니라 후속 개발 범위입니다. 기존 데모의 안전장치를 제거하거나 미구현 기능을 제공한다고 표시하지 않습니다.

현재 대표 기능·배포·상태 조회는 부분 검증됐고, 원격 빌드 연결·공통 확장 계약·독립성 및 새 환경 재현 검증은 남아 있습니다. 뼈대 기준의 새 퍼센트는 이 완료 조건을 대조한 뒤 산정합니다.

## 전체 기능 목표의 이전 추정

**전체 진척도는 약 30%(25~35% 범위)로 추정했습니다.** 완료된 티켓 수나 일정 소진율을 측정한 값이 아니라, 현재 확인한 결과와 남은 주요 기능의 크기를 반영한 엔지니어링 추정입니다. AWS의 모든 최신 기능과 완전한 성능 동등성은 분모에 넣지 않았습니다. 기존에 요구한 주요 기능과 반복 배포 가능한 파일럿을 기준으로 하며, 실제 고객 운영 준비는 별도 검증이 필요합니다.

## 최근 실제 확인한 결과

2026-11-06 staging 점검: bootstrap에 root 소유/쓰기 제한·symlink 거부와 실제 ocarun 경로 통과·쓰기 검사를 추가했습니다. 읽기 전용 `--check`가 서울 VM에서 통과했고 앱 UP·0.4.2를 유지했습니다. 분리된 Linux 임시 경로에서 과거 0700 상위 경로 장애의 차단, 자동 chmod 없음, 정상 경로 통과, 공유 쓰기 거부를 검증했습니다. 배포 도구 검사 59개와 하위 검사 3개 통과. 후속으로 사전 점검을 포함한 bootstrap을 적용하고 OCI SDK에서 기존 0.4.2 재배포를 요청해 SUCCEEDED를 확인했습니다. 새 검증 CLI로 모델·메모리·인증·버전·추적 통과 및 기존 기억 보존을 확인했습니다. Companion UI 요청과 신규 버전 빌드 검증을 뜻하지 않습니다.

구축 문제를 재사용 기능으로 전환하는 [운영 개선 백로그](operations-improvements.md)를 관리합니다. 구현 완료·환경 적용·후속 기능을 구분합니다.

2026-11-06 Companion 로그 사전 점검: 두 빌드 실행 경로에서 활성 로그 확인 후 요청하도록 구현했습니다. 비활성·미발견·조회 실패를 구분하고, 실제 서울 프로젝트 READY 및 전체 검사 114개를 확인했습니다. IAM 정책 한도 해결 가이드도 추가했습니다. 정책 자동 점검·수정과 새 안내의 브라우저 검증은 남아 있습니다.

- Companion을 중지한 상태에서도 OCI 메모리 기존 기록 조회가 통과했습니다. 모델·모든 도구의 중지 중 독립성까지 시험한 것으로 확대하지 않습니다.
- 후속 SDK 관리형 빌드는 명세 검사를 통과했으나 GET_BUILD_RUNNER에서 실패했습니다. OCI 상세 메시지는 `Unable to get Build Runner, please try again.`이며 현재 로그만으로 할당 실패의 근본 원인을 확정할 수 없습니다. 기본 러너로 두 번 같은 단계에서 실패했고, 동일한 2 OCPU·8GB를 명시한 별도 할당도 같은 GET_BUILD_RUNNER 단계에서 실패했습니다. 세 실행 모두 빌드 명령 실행 전 실패했으며 추가 반복 실행은 중단했습니다. 현재 파이프라인은 명시적 2 OCPU·8GB 설정을 유지합니다. Companion 재시도는 Edge 확장 UI 차단으로 검증하지 못했습니다.

이는 관리형 빌드·Registry 전달·새 버전 배포의 완주가 아닙니다. 실행 중 앱은 기존 0.4.1을 유지합니다. 아래 기존 조사 중 빌드 저장소/파이프라인 부재와 커밋 하드코딩은 이번 구현으로 해소됐습니다.

- 새 bootstrap VM 전용 파이프라인을 Companion 화면에서 실행하여 동일 0.4.1 재배포 SUCCEEDED를 확인했습니다.
- Companion 모니터링에서 새 VM UP·0.4.1 및 모델·승인·메모리 실행 추적을 확인했습니다. 로컬 SSH 터널과 합성 계정을 사용합니다.
- 재배포 후 Oracle Agent Memory 기존 기억 검색 검증이 통과했습니다.
- 새 VM 첫 부팅·재부팅 보존은 검증했으나 첫 설치 오류를 관리자 수정한 이력이 있습니다. 수정본으로 또 다른 빈 환경을 무개입 구성하는 재현은 아직 하지 않았습니다.
- 초기 조사에서는 빌드 저장소·파이프라인이 없었으나 후속 작업으로 생성했습니다. 외부 Git 연결 대신 OCI 입력 스냅샷을 사용합니다. Companion을 통한 새 버전 빌드 완료로 표시하지 않습니다.

## 바로 다음 작업과 완료 기준

1. 고정된 Launchpad 소스와 Python Foundation 버전을 입력으로 받는 빌드 계약을 만듭니다. `deploy/package_sources.py`의 커밋 하드코딩을 제거했고 Foundation 0.1.2 고정 소스 빌드를 확인했습니다. 관리형 빌드의 최종 실행·전달 검증을 이어갑니다.
2. Linux x86_64/Python 3.12에서 테스트·wheel 생성·고정 의존성 수집·manifest와 ZIP 생성을 실행합니다. 소스 커밋, Foundation 버전, 빌드 ID, 패키지 SHA-256을 기록합니다. 개인 PC의 Git/OCI 인증 파일은 빌드 입력에 넣지 않습니다.
3. Companion에서 빌드 요청과 결과를 조회하고 불변 릴리스를 배포 대상으로 넘깁니다. 현재 root 소유 허용 manifest 수동 등록을 대체할 승인 계약도 필요합니다. 이 연결은 아직 구현하지 않았습니다.
4. Companion에서 빌드한 **새 버전**을 새 VM에 배포하고 같은 릴리스의 health·대표 업무·메모리·실행 추적을 확인하면 이 단계가 완료됩니다. 기존 버전 재배포만으로 통과 처리하지 않습니다.

플랫폼 독립성은 별도 검증합니다. Companion이 없어도 문서화된 API/CLI로 앱을 호출할 수 있고, Companion 중지 중에도 플랫폼의 모델·메모리·도구 호출이 동작해야 합니다. 두 프로젝트가 공통으로 사용하는 계약은 버전을 붙이며 Companion 전용 세션이나 내부 파일을 플랫폼 런타임의 필수 의존성으로 두지 않습니다.

자세한 책임 구분은 [플랫폼과 Companion 연동 범위](companion-agent-platform-review.md)를 참고하세요. 아래 내용은 당시 검증 이력을 보존한 것으로, 현재 남은 기능 목록은 위 내용을 기준으로 봅니다.
