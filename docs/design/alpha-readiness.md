# OCI Agent Launchpad 알파 제공 범위와 출시 판단

고객 업무를 함께 정의하고 작은 에이전트를 OCI에 배포·관측하는 **엔지니어 동행 알파**로 제공할 기술 근거가 있습니다. 고객이 혼자 설치·운영하는 셀프서비스 제품 또는 AgentCore 전체 대체 제품으로 소개할 단계는 아닙니다. 2026-11-09 저장소와 실제 Hello Agent 검증을 바탕으로 한 판단이며 출시 승인을 대신하지 않습니다.

## 누구에게 무엇을 제공하는가

대상은 OCI 엔지니어 또는 CE와 함께 참여하는 개발팀입니다. 합성 데이터와 비핵심 업무 한 가지부터 시작하고, 인터뷰 템플릿으로 성공 기준을 정한 뒤 구현·OCI 빌드·배포·시험·관측을 진행합니다. 고객은 코드, 설정, 실행 증거, 알려진 제한과 운영 전 보완 목록을 받습니다. 처음에는 준비된 개발 환경에서 진행하며 아무 테넌시나 즉시 설치된다고 약속하지 않습니다.

제안 소개 문구: “고객과 함께 에이전트를 만들고 OCI에 배포해 실제 동작과 추적을 확인하는 개발·검증용 알파입니다. OCI 구성요소를 우선 사용하고 필요한 부분에 오픈소스를 연결합니다.”

## 입증한 가치와 범위

| 항목 | 확인한 사실 | 해석의 한계 |
|---|---|---|
| 실제 배포 흐름 | Companion에서 Functions 소스 빌드, Managed Build 패키징, OCIR, 서울 OKE 배포 | 준비된 자원·권한에서 수행; 빈 환경 자동 설치를 입증하지 않음 |
| 웹에서 업무 실행 | Hello Agent 질문 → OCI 모델 → 허용 도구 → 실제 시각 응답 | 작은 읽기 전용 업무; 자율 복합 업무나 일반 고객 정확도는 미검증 |
| 관측 | 같은 웹 실행의 모델·도구·응답 입력/출력 Langfuse 조회 | 실패 호출 추적·재전송·유실 방지는 미완료 |
| 관리 독립성 | Companion 등록 정보로 health·버전·Pod·노드 조회 | 관리 PC 터널 의존; 상시 수집·알림과 다름 |
| 검증 Job | Companion 화면에서 시작한 Job Complete와 모든 검사 PASS | 결과 수집은 운영자가 수행; Companion 자동 수집은 미구현 |
| Companion 회귀 | Job 지원 변경 포함 159개 테스트 통과 | 테스트 수가 보안·운영 성숙도를 보장하지 않음 |
| 요구·인수 설계 | 고객 여정·필수/옵션 템플릿과 제품 명세 존재 | 인터뷰부터 운영 인수까지의 통합 고객 화면은 미구현 |

Hello Agent는 Memory가 필요 없는 예제입니다. 기존 Service Desk의 메모리 통합 근거와 별도로 판단합니다. ContextForge·OPA 등 후보를 아키텍처 문서에 적었다고 통합 완료로 표시하지 않습니다. 상세 근거는 [Hello Agent 인수 기록](../../examples/hello-agent/DELIVERY.md)과 [고객 전달 명세](customer-delivery-spec.md)를 확인합니다.

## 알파 유형별 판정

| 제공 방식 | 현재 판단 | 필요한 조건 |
|---|---|---|
| 내부 기술 시연 | 가능 | 합성 계정, 터널, 비용·대상 환경 확인 |
| 엔지니어 동행 고객 알파 | 제한적으로 가능 | 시험용 업무·데이터, 담당 엔지니어, 수작업 설정·제약 고지, 고객별 환경 사전 점검 |
| 고객 셀프서비스 알파 | 보류 | 다른 엔지니어가 새 환경에서 문서만으로 설치·검증·정리 재현 |
| 운영 서비스/AgentCore 완전 대체 | 부적합 | 업무별 인증·격리·평가·알림·복구·성능과 기능 공백 해소 |

## 첫 외부 알파 전에 끝낼 일

1. **릴리스 묶음 고정:** 서로 독립적인 Launchpad·Companion·Foundation의 호환 버전, commit, 배포 이미지 digest를 고정합니다. 아직 커밋되지 않은 작업 파일에 설치가 의존하지 않도록 확인합니다.
2. **첫 성공 절차:** 한 가지 기본 배포 경로에서 준비 입력, IAM·네트워크·용량 사전 점검, 빌드·배포·등록·질문·trace 확인 절차를 정리합니다. 수작업 단계는 숨기지 않습니다.
3. **독립 재현:** 기존 개발자 외 엔지니어가 별도 시험 환경에서 이 절차를 따라 성공하고, 설치 실패의 원인과 복구 경로까지 기록합니다. 아직 수행되지 않았습니다.
4. **인수 범위:** 지원 기능·제외 기능, 사용자/서비스 인증, 입력·출력 수집 범위, 모델 처리 리전, 비용 부담, 문의 담당자를 명시합니다.
5. **정리·복구:** 시험 자원 식별, 비용 중지·삭제 대상, 보존할 데이터, 이전 릴리스 복구 절차를 재현합니다. 공유 자원과 고객 데이터를 일괄 삭제하지 않습니다.

이 항목들은 출시를 위해 무조건 큰 고객 포털이나 새로운 DB를 만들라는 뜻이 아닙니다. 버전이 고정된 문서·설정·CLI와 기존 GUI 연결로 먼저 완주하도록 합니다.

## 알파 후 보완 순서

- 1순위: Job UID·실행 ID·명세 digest와 결과 JSON을 연결해 배포 성공/검사 통과/운영 인수를 구분합니다. 현재 Job 실행 지원과 결과 자동 수집은 다른 기능입니다.
- 2순위: 고객별 인증·비밀 관리, 사설 접속 절차, 오류 추적과 관측 실패 처리, 비용·시간 제한을 보완합니다.
- 3순위: 대표 업무 평가 사례, 운영 알림·복구 시험, 인터뷰→진행→인수 화면을 작은 단위로 추가합니다.
- 선택 기능: Memory·Gateway·정책·코드·브라우저 실행은 고객 업무에서 필요할 때 OCI 우선으로 조합하고, 확인된 공백만 OSS로 보완합니다.

완료율 하나보다 “어떤 사용자가 어떤 환경에서 무엇을 끝낼 수 있는가”와 그 증거를 출시 기준으로 사용합니다.
