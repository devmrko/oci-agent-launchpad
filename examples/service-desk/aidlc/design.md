# 사내 안내와 요청 접수 예제 설계

2026-11-05. 사용자 지시로 제작하는 합성 업무 예제입니다. 고객의 실제 요구 승인이나 운영 검증을 대신하지 않습니다.

## 의도와 예시 답변

가상 고객: 직원이 장비·접속 규정을 찾아보고 필요하면 지원 요청을 제출하고 싶습니다.

| AI 확인 질문 | 설명용 고객 답변 | 설계 영향 |
| --- | --- | --- |
| 규정 밖 질문은 어떻게 처리합니까? | 근거가 없으면 모른다고 답합니다 | 근거 검색과 응답 제한 |
| 바로 요청을 등록합니까? | 등록 내용을 본 후 확인합니다 | 제안 생성과 승인 실행 분리 |
| 누구의 요청을 볼 수 있습니까? | 자신의 요청만 봅니다 | 인증 주체로 조회 범위 강제 |
| 기억할 정보가 있습니까? | 동의한 선호 언어만 기억합니다 | 명시적 장기 기억 쓰기·읽기·삭제 |
| 실제 사내 시스템에 연결합니까? | 첫 예제는 가상 접수함입니다 | 외부 부작용 없이 실제 DB 등록 검증 |

## 구조와 책임

Router → Service → Repository. Foundation의 Actor, Security, install_web, SqlAlchemyUnitOfWork와 DB factory를 재사용합니다. 예제 고유의 규정 검색과 접수 규칙만 앱에 둡니다. 공통 범용 에이전트 SDK를 이 예제 안에 새로 복제하지 않습니다.

API는 세션 생성, 대화, 제안 승인, 접수 조회, 선호 언어 조회·변경·삭제, 실행 기록 조회로 나눕니다. 인증 subject와 issuer로 소유자를 결정합니다. 제안 내용을 승인 요청에서 다시 받지 않아 승인 후 내용 바꾸기를 차단합니다. 제안 ID가 접수의 유일 키가 되므로 중복 등록을 차단합니다.

모델은 도구 선택을 제안할 수 있으나 허용된 동작만 서버에서 실행합니다. 기본 데모는 결정적 규칙 라우터이며 LLM 추론을 수행했다고 표시하지 않습니다. 실제 모델은 외부 HTTP 엔드포인트와 모델 이름을 설정했을 때만 사용합니다. 코드·브라우저 격리 실행은 이 예제에서 비활성이고 플랫폼 전체의 미구현 목표로 남깁니다.

## 작업 단위와 검증

- Unit 1: 인증·소유권·상태 저장. HTTP 인증 거부, 교차 사용자 접근, 재시작 시험.
- Unit 2: 규정 검색·도구 제안·승인 등록. 무관 질문, 승인 전 부작용, 변조 요청, 반복·동시 승인 시험.
- Unit 3: 기억·추적·평가. 다음 세션 기억, 삭제, 응답 요청 ID 연결, 로그 민감정보 검사.
- Unit 4: 패키징·Companion 설치·배포 계약. 설치와 실제 OCI 배포 여부를 독립 기록.

첫 로컬 검증은 플랫폼의 9개 주요 기능 완료를 의미하지 않습니다. 실제 OCI 호출, MCP 네트워크 Gateway, OAuth 위임, 강한 sandbox, 확장·스트리밍, 운영 평가·APM 연결은 각각 추가 검증 대상입니다.

## 진행 기록과 원문 근거

설계서를 코드보다 먼저 작성했습니다. 예시 답변은 작성자가 만든 합성 답변이며 실제 고객 승인으로 기록하지 않습니다. 사용자는 예제 제작·진행과 Companion 설치를 요청했습니다.

## 0.2 설계 보완

공통 도구 계약은 Foundation 0.1.1에 둡니다. 앱의 세션 소유권을 확인한 뒤에만 모델로 입력을 보내며, 모델 선택은 search/propose로 제한합니다. 승인 API는 별도 사용자 입력을 받고 공통 Gateway에서 권한·자원 소유권을 다시 검사합니다. 성공·실패 실행에 동일 run_id의 도구 이벤트를 저장합니다. OCI 모델 응답의 finish_reason과 JSON 계약을 확인하고 잘못된 응답은 도구 호출로 전환하지 않습니다.
